这篇文章只聚焦两个问题：媒体加载如何从「重、抖、慢」变成「按需、稳定、可控」，以及首屏加载如何从「资源拥堵」变成「更快可用」。这不是一次单点调参记录，而是一套可以在项目里复用的优化路径。页面真实运行中最典型的现象是，内容已经开始渲染，但关键文本和交互往往被图片、视频、非当前路由代码抢占资源，用户会明显感知到「能看到页面，但不够快；能滑动内容，但不够稳」。因此本文所有方案都围绕一条原则展开：先保证关键路径，再加载次要内容，最后用调度控制高频重算。

## 媒体加载优化：先控制时机，再控制计算

媒体相关性能问题最棘手的地方，不在于单个图片或单个视频有多大，而在于它们通常同时出现，并且会叠加布局计算。图片如果默认立即请求，会和首屏关键样式、关键脚本竞争网络；视频如果在不可见状态下就初始化解码，会持续消耗主线程和硬件资源；轮播在 `resize`、方向变化、资源加载完成时如果同步重算，会在短时间内触发多次回流，最终表现为可见抖动。因此媒体优化的核心并不是「压一个资源」，而是把「请求时机、激活时机、重算时机」全部纳入约束。

在图片侧，策略非常直接：统一使用延迟加载和异步解码，让浏览器把非关键图像放到更合适的调度队列中。实现层面不复杂，但必须保证默认策略一致，否则个别组件回退到 eager 加载会迅速破坏整体收益。典型输出如下，`loading='lazy'` 与 `decoding='async'` 配合可以把非关键图片从首屏竞争队列里移开，先让关键文本和基础布局到位。

```html
<img src="..." loading="lazy" decoding="async" />
```

在视频侧，关键点是「可见性门控」。如果视频不在视区内，就不应进入重路径。当前实现通过 `IntersectionObserver` 跟踪可见比例，在进入阈值后再激活播放相关流程。对于轮播内部视频，还会叠加轨道内可见比例约束，避免边缘视频提前占用资源。这样处理以后，视频成本从「页面级常驻开销」变成「用户接近内容时的按需开销」，体感会明显更稳定。

```js
const viewportObserver = new IntersectionObserver(onViewportChange, {
  threshold: [0, 0.15, 0.35, 0.55, 0.75, 1],
});
```

仅仅门控还不够，媒体页面通常还需要处理对齐和尺寸重算。若每次事件都同步执行布局计算，性能会在交互高峰时恶化。这里的做法是把重算统一调度到 `requestAnimationFrame`，并加两次短延时结算，覆盖图片元数据晚到、视频首帧就绪等异步状态变化，减少「先对齐一次、再跳一次」的问题。这个方法看起来只是把函数换了入口，实际价值是把零散同步计算收敛成有节奏的帧内任务。

```js
const scheduleAlign = () => {
  requestAnimationFrame(() => {
    alignMediaCarousels();
    alignTimer = window.setTimeout(alignMediaCarousels, 80);
    alignSettleTimer = window.setTimeout(alignMediaCarousels, 280);
  });
};
```

这条链路落地后，验证不建议只看单一分数，而应该看三个连续行为：首屏期间非关键媒体请求是否明显后移，滚动进入媒体区域时视频是否按可见性激活，以及频繁 resize/旋转后轮播是否仍能稳定对齐。只要这三点稳定，媒体优化基本就进入可持续状态。

## 首屏加载优化：减少首屏阶段的传输和执行竞争

首屏慢通常来自两类开销叠加，一类是传输体积过大，另一类是首屏执行内容过多。实际项目里，前者主要来自图片资源管理不统一，后者主要来自未按路由切分代码。两者共同作用的结果是，页面虽然已经开始请求，但关键可见内容和可交互时间被推迟，用户会感觉页面「启动迟缓」。首屏优化因此不应从零散组件入手，而应从构建输出和运行时加载策略两端同时下手。

构建端先做减重，把图片优化前置到构建流程，避免人工压图的不稳定性。项目中使用 `vite-imagetools` 与 `vite-plugin-image-optimizer` 作为统一链路，压缩和去元数据都由配置驱动，新增素材自动纳入同一策略。这样做的收益并不只是一版体积下降，而是后续内容迭代不会轻易反弹。

```js
import { imagetools } from 'vite-imagetools';
import { ViteImageOptimizer } from 'vite-plugin-image-optimizer';

plugins: [
  imagetools({ removeMetadata: true }),
  ViteImageOptimizer({
    includePublic: true,
    png: { quality: 80 },
    jpeg: { quality: 80 },
    jpg: { quality: 80 },
    webp: { quality: 80 },
  }),
]
```

运行端再做减负，把非当前页面代码移出首屏执行路径。具体做法是路由组件统一改为动态导入，首屏仅加载当前路由必要代码，其他页面在访问时再加载。这样首屏解析和执行压力会明显下降，尤其对移动端设备更敏感。

```js
{ path: '/news/:id', component: () => import('../views/NewsArticlePage.vue') }
```

这一步完成后，验证重点应该落在「关键内容更早出现」和「切路由不放大卡顿」两个层面。前者说明首屏路径被净化，后者说明分包策略没有把成本推迟成新的体验问题。

## 如何把这两条优化路线落地成教程步骤

如果把上面的经验收敛为一条可执行路径，最稳妥的顺序是：先把构建链路收紧，再把路由按需加载补齐，然后处理媒体门控，最后统一高频重算调度。这个顺序可以确保每一步都有清晰收益，并且不会因为先做复杂交互而掩盖基础收益。换句话说，先「减体积和执行负担」，再「减无效媒体开销」，最后「抚平交互抖动」。

在执行过程中还有一个常见误区需要避免：把优化看成一次性动作。真正有效的优化一定要变成默认规则，例如图片优化必须是构建默认行为、路由按需加载必须成为代码规范、媒体激活必须由可见性驱动、布局重算必须走统一调度入口。只有这些规则固化下来，后续新页面和新内容接入时才不会把性能再次拉回原点。

## 总结

媒体加载优化解决的是「重内容如何按需激活」，首屏加载优化解决的是「关键内容如何更早可用」。两者本质上都在做同一件事：把不可控开销变成可调度开销，把临时修复变成工程默认。当前实践证明，当构建减重、路由分包、媒体门控和帧调度同时成立时，页面不仅更快，也更稳，用户感知会从「功能可用」提升到「体验顺滑」。这也是前端渲染性能优化真正应追求的结果。
